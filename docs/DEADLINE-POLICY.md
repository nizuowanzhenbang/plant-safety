# 隐患整改期限规则

本项目示例规则：重大隐患最多 14 天，一般隐患最多 30 天，均从 `reported_at` 发现时间起算。该规则沿用项目 CLAUDE.md，不代表替现场制度制定新标准。

## 本轮确定的行为

- 手工创建与检查转换：发现时间由服务端一次取值；不传期限或传 null 时按等级补默认期限。
- 手工填写的截止时间可以等于上限，晚于上限返回 422，不写入记录。保留已有的过去日期录入与超期识别，不新增截止时间下限。
- 检查转换 `deadline_days` 仅接受 1 到对应等级上限；省略/null 使用等级默认值，0 不再当成默认值。
- 修改明确期限时，按数据库里的发现时间和修改后的等级校验；不能从本次请求时间重新获得 14/30 天。
- 修改期限为 null 表示重置为发现时间起算的等级默认期限，不表示取消期限。
- 改变等级但省略期限时，保留符合新等级的现有期限；旧期限超出新上限则返回 422，要求同一请求提供合规期限；旧期限为空则补新等级默认值。
- 老记录的原期限超限或为空时，更新标题、整改措施等无关字段仍可进行；不自动批量改写历史数据。显式修改期限或实际改变等级时才应用本规则。
- 时区输入先换算到 UTC；现有不带时区的数据库字段继续使用 UTC naive，不做数据库迁移。
- 外部设备集成仍保留 CRITICAL→重大、其他→一般、重复返回原隐患的语义；新记录的发现时间与默认期限使用同一个锚点。
- 已关闭记录、权限规则和安全检查关联保护沿用现有行为。
- 手工更新以校验时的等级、发现时间、期限、状态及更新时间为条件进行原子写入；竞争请求改变记录后，过时更新返回 409，要求刷新后重新校验，不部分覆盖记录。

## 验证范围

真实 HTTP、JWT、SQLite 临时数据库回归覆盖创建/修改/转换/集成，拒绝后全部隐患和检查记录不变。日期上限、微秒边界、UTC 偏移、等级改变、旧记录、默认值及重复返回分别验证；原检查关联与写入回滚测试继续运行。并发回归确定性地调度真实请求交错，覆盖等级与期限的两种竞争顺序，以及校验后另一请求完成复查关闭。

本轮没有 PostgreSQL 运行时验收、现场验收、历史数据修复或跨系统可靠投递承诺。输入、规则、结果和接续证据记录在 smart-power-plant/progress/。
